## 1 · The contract

1. **Statuses are honest.** Every entry carries exactly one: **shipped** (ratified and in this tree at the named path) · **forging** (being built, in a named place — possibly another instance's jurisdiction) · **named** (demanded with recorded provenance, not started). A registry that fakes a status has broken its one job.
2. **Prose + checker, or it is a norm.** Per the Network Foundation's rule (§5, welded limit 3): *a standard without a checker is a norm, not a gate.* Each shipped entry names its checker half — or says **prose-first** and names the checker's build trigger. Both are legitimate; silence is not.
3. **Adopt before invent — the registry is the shelf.** C-092 extends here: before building any procedure, format, or convention, a session checks this catalog first and offers the existing entry. Build new only knowingly, after the check.
4. **Growth is by ratified decision.** An entry joins when the instance that forged it ratifies it; demand joins as a **named** row citing its provenance (finding ids, fieldnote entries, wishlist items). Foreign forges are listed honestly with their jurisdiction (the KNet precedent).
5. **Adoption is sovereign and recorded.** To adopt: read the standard at its canonical path → record the adoption as your own decision (`P-…`) → copy or bind any tool half → run its checker if one ships. A never-adopting instance is fully conformant; a silently-adopting one is not. **The prose half's post-adoption residence is part of the recorded decision:** either the standard's document joins the adopter's governance tree as an inherited copy at its pinned edition (appended to `.inherited` in the same change-set), or it is cited at the pinned anchored release (accepting the retained release copy — frozen clone or Git bundle — as a rehydration dependency); the adopter's self-containment rule decides which. (The KNet precedent: nine standards copied in at their beta-0.5 editions, plus a hash-pinned Git bundle of the signed tag as the retained release pack.)

**The integration categories (C-127 — Max's separation of record, 2026-08-19; scoped per Scan #6 S6-7.5).** Every *adoptable* concept and tool sits in exactly one **integration category**, defined by how deep it integrates into an instance. (The scope is adoption: records — protocols, Return Packages, store history — fall to Architecture State §6's biography class and are never adopted; environment and config to the working-environment layer, C-087. C-127 answers what *adoption* means; AST §6 answers what *inheritance* means.)

| Category | Integration | State |
|---|---|---|
| **Kernel concept** | ships with every birth — the constitution, formats, and procedures of the GENESIS §5 shelf | in use — the shelf's current stock |
| **Kernel tool** | ships with every birth — the store's copied tool set (GENESIS §1: `verify.py`, `genesis.py`, `close.py`, …) | in use |
| **Custom concept** | an instance's own organ, grown on felt need (the pair-extension class) — **never released**: the C-116 curated sync excludes custom-concept artifacts; the stranger meets the *class* in the site's story, never an instance's copy (the mother's Update Plan pair the specimen) | in use |
| **Installable tool** | installed into a fractal by its owner's recorded decision, running in the host's own sessions — Foundation v0.4's installed-integration mode (pinned releases, the uninstall floor) | **banked ahead of need** — the Mining Tool forging as the first member (§5) |
| **Plug-in** | integration without installation — the loosest form | **banked ahead of need** — named only, not designed |

The category is not a status (rule 1 keeps that job); it answers a different question — *what would adopting this mean for my instance*. The two banked categories are formulated, never built ahead of need (C-021).
