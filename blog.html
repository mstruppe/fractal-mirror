The idea

Real investigation is fragmented. A question moves through the web, the literature, a dataset, a notebook, a model, a draft — and every switch throws context away. The answer half-formed on one surface has to be rebuilt on the next. FRACTAL began as a refusal to accept that: one environment for the whole lifecycle — gather, organise, analyse, model, connect, communicate — where the reasoning survives along with the results.

The method behind it is recursive simplicity. Complex understanding comes from a small set of simple rules applied again and again, at every scale: project, domain, component, conversation, task. Begin from the smallest abstraction that works, and add only what an observed problem demands. The same principle decides what gets built at all — nothing in the system exists ahead of a need that actually fired.

The AI in this picture is a collaborator with the books open. It drafts, maintains, verifies, and cites; interpretation and decisions stay with the human. And the knowledge itself is treated as a living structure rather than a pile of documents — everything connects, everything carries its provenance, nothing depends on anyone’s memory.

How it started

FRACTAL began as long conversations with an AI about how knowledge work should feel, and became software the day those conversations were given a repository. The earliest foundation — the first architecture drafts, the first governance protocols — was laid with one vendor’s chat assistant; in August 2026 the project moved to a coding agent and rebuilt itself from first principles. That era split is preserved in the repository’s own archive, because the project keeps its history the way it keeps everything else.

The first thing built was memory: a knowledge store of small, append-only records with a verifier that blocks any commit violating its invariants. The second was law: every decision the project makes is a numbered row in a register, with its reasoning attached — made by saying it out loud in a working session. Rules are made by talking; the record keeps them.

Around those two grew the rhythm the system still runs on. A session opens by reading a compressed spine of context — the vision, the current state, the standing rules. It closes by writing its own record: what was decided, what changed, what the next session should expect. The close is a ritual with machine checkers that block red, and it ends in a commit. Between sessions, nothing lives in an AI’s memory; everything lives in the repo.

How it developed

The system’s first real test was reproducing itself. The kernel — the constitution, formats, procedures, and tools a project needs from day one — was extracted into an executable genesis, and the stranger’s path from a bare clone to a working instance was drilled until it held. The first child followed: a research project born from an anchored release tag, governed by its own record from its first session. It later crossed a release boundary under its own migration protocol, every gate on the record — and along the way it swapped AI vendors mid-life without touching the kernel.

Releases became provenance events: each one a signed tag with an independent OpenTimestamps receipt committed beside it, the earliest anchors Bitcoin-final. Five betas shipped that way. On 18 August 2026 the proven parts went public — a mirror serving the anchored releases, this site explaining the machine from its real parts, one permanent address as the door. Live is deliberately not official: no announcement, no launch. The system keeps improving the way it always has — by being used, now in the open.

What follows are the claims that record can already back.

Proof — claims you can check

The memory survives a vendor swap

The first project born from FRACTAL’s kernel was birthed and run through Claude Code, then continued its working sessions in the ChatGPT desktop app — zero kernel changes, because the memory lives in the repo. The protocol of record states: “Client-neutrality moved from claim to observed fact.” In the founder’s words: “usually you’re vendor bound to get memory within projects.”

Integrity is machine-verified, not asserted

Two dependency-free checkers block red: one verifies the knowledge store’s invariants before every store-touching commit; one reads the corpus’s own prose claims about itself — versions, pointers, counts — against reality at every close. Both have caught real defects, and each catch becomes a mechanical rule. The tools refuse, never degrade. Where the checkers don’t reach, verification stays on humans — the machine-checked claims run in minutes; the rest is reviewed on the record, and drift is measured, not denied.

Total machine loss is drilled, not promised

A fresh clone on a clean machine rebuilds the working system from the bootstrap document alone — verified, byte-parity, three green drills on the record. The record’s own words: “‘Laptop in the ocean’ is demonstrated fact.”

Priority is mathematics, not testimony

Every release ships as a signed tag with an independent OpenTimestamps receipt committed in the repository itself, so a clone of the public home carries the proof chain for every anchored release before it (the newest tag’s own receipt lands with its anchor commit); the earliest anchors are Bitcoin-final. This is the one claim a stranger can check without reading anything — both commands from a clone’s root:

git -c gpg.ssh.allowedSignersFile=.allowed_signers tag -v beta-0.4

ots verify Provenance/beta-0.3-public.txt.ots

The first needs only git — the flag binds the repository’s own signer roster, and a good signature prints as such. The second needs the OpenTimestamps client (pip install opentimestamps-client); without a local Bitcoin node it retrieves the calendar attestations and then reports it cannot reach a node — that is the expected view from a fresh machine, and the pending-versus-final status it prints is the honest state of each anchor.

A stranger can birth a working instance

The path the setup describes has been walked twice under stranger conditions: once when the first child project was born from an anchored release tag, and once in a simulated onboarding of the public mirror itself — a scripted non-programmer ran the quickstart verbatim through to a real birth, both integrity checkers passing, with no outside knowledge needed at any step.

Limits, stated

FRACTAL does not abolish context limits — sessions read a compressed spine; the claim is owned, verifiable, vendor-independent memory, never infinite memory. No auto-updates into living instances — by design; sovereignty is the trade, named plainly. No adoption path for existing projects yet — the paved path births new projects. No UI — terminal and files, with one honestly failed experiment on the books. The network layers are unbuilt and trigger-armed, constitutionally barred from binding a build.

Stories from the record

Dated episodes from the project’s own history, told with their evidence attached — appended as they happen, never rewritten.

2026-08-20 — The release that caught itself

Shipping beta-0.6, the release ritual made a mistake and then caught it, inside the same sitting. Both halves belong in the story.

The public home keeps two proof chains by design: every release of the private repository is signed and externally timestamped, and the public mirror carries its own timestamp receipts on top — checkable in their own domain, without access to anything private. Those public receipts live only in the mirror; a release tree structurally cannot contain the attestations of its own chain. The rebuild step didn’t know that. Its sync mirrors the fresh release exactly and deletes whatever isn’t in it — so it swept away the public chain’s three receipt pairs, and the rebuild commit dutifully recorded their deletion.

The catch came one step later, because the ritual’s next step is a reader. Writing a new release’s attestation starts by reading the previous one, to reproduce its exact shape. The read came back empty. The mirror’s own history showed the three commits that had anchored those receipts; a diff of the fresh rebuild showed it deleting them. The automation made the mistake; the ritual caught it, because every step reads the record before it writes.

The cure took minutes, and the reason it could is the system’s oldest rule: nothing is ever overwritten. Nothing had been pushed yet — the gates run before anything leaves the machine — so the defect existed only in one local commit. The receipts were restored straight out of the parent commit’s tree, the rebuild was amended, the release tag re-signed on the corrected state, the pack gate re-run green, and only then did anything publish. The public history never carried the defect; the shipped beta-0.6 chain contains all four public receipts, and this paragraph is checkable against it.

What remains is the lesson, written down: the rebuild’s preservation duties named two protected classes, and reality holds a third — the mirror’s own receipts. The finding stands on the record with a named cure: the pack gate grows that third check the next time the tooling moves. A mistake, a catch, a clean recovery, and a rule that got sharper — that is the loop this whole system is built to run.

Where it is heading: three branches and a shooting star

The forward path is written the same way as the history above — with statuses attached. Its core is the value model: what FRACTAL is worth, and to whom. Deliberately not a business model — business implies cash flow, and none of the branches below carries one. It is a value promise: the structure of what the project delivers before, and independent of, any money changing hands.

The branches share a structural property that is itself fractal: each is a value promise outward and an experiment inward, at once. The product proves itself by running its own development. The explanation of the machine is built from the machine’s real parts. The distribution arm, when it opens, will double as the test bench for a content class the system has never governed. Nothing here is decoration on top of the work — every surface that delivers value to someone else also feeds the loop that improves the system.

The product: memory that survives

The kernel, the governance stack, the knowledge store, the standards. The promise is the one on the masthead — AI agents forget. Your project won’t. — made provable rather than asserted: session-durable context, decision provenance, machine-verified consistency, releases signed and externally timestamped. It is the deepest branch and the furthest along: every release since the first anchored, an executable genesis, and a first foreign project born from the kernel and later migrated across a release boundary under its own governance — every gate on the record.

Everything else in this model rides on this branch. No other promise is credible if this one is not real — which is why the proof chapter exists.

The hub: the site is the engine sketch

This website is not marketing surface for branch one. It is the machine’s explanation built from the machine’s real parts — the shipped baseline’s command files and working standards, verbatim and downloadable, refreshed with each release. Its standalone promise: a visitor can learn the method, take the standards, and adopt pieces without ever birthing an instance.

That promise is not a guess. In a simulation program, three synthetic adopters walked the public material end to end; all three declined the full system — not yet — and all three wanted the substrate: the standards, the procedures, the checkable formats. People take the parts before they take the whole. The hub is the branch that serves exactly that adoption path, and it grows by the ordinary content pass — guide depth, paper-style standard pages, field studies.

The media branch: declared, unbuilt

The newest branch, and the only one that does not exist yet — stated here with its honest status. Three roles in one structure: marketing, website extension, and information distributor — a social media arm producing governed public content.

Its inward face is the interesting one. Producing governed media content means solving, in real use, problems no current part of the system touches: extracting knowledge from media into the project’s markdown record; whether a post is a stamped projection of a canonical source, the way every other public artifact here is; provenance for content that leaves the repository and circulates; and the complexity growth of the instance that governs all of it. Somewhere there is a practical limit to how complex a governed instance can get. None is in sight yet — and this branch is the probe that goes looking for it.

It opens by decision, not by drift: no post exists until the branch’s trigger fires, and when it does, the experiment is instrumented from the first post — the same field-testing discipline every other part of the system runs under.

The horizon: the shooting star

The fourth value is the knowledge network — warm starts for every new project, knowledge exchanged as verified increments, verification labor finally paid. It is deliberately not a branch. It is a bearing: the direction the three branches fly by, not a destination any of them is committed to reach. The network layers are unbuilt, trigger-armed, and constitutionally barred from binding a build — the same honesty the limits section states for everything else. The nearest real piece of it already exists in miniature: one public home, serving standards to anyone who wants them.

The constraint: gas

One constraint cuts across every branch, and it deserves to be stated as plainly as the promises: this work is token-heavy, and tokens are not cheap. The record carries the data honestly — a single nine-agent verification flight spent close to a million tokens; the largest verification program ran 67 agents; the flight standard requires cost reporting precisely because the burn was felt early. The structural form of the risk is sharper than “expensive”:

Value scales with token spend — so the failure mode is not that FRACTAL doesn’t work, but that it succeeds into unaffordability. FRACTAL could become so good it needs too much gas.

The exposure differs by branch: the product’s ritual overhead is the baseline burn; the hub is nearly free — static content, refreshed mechanically; the media branch would be the hungriest of all, which is one reason it waits for a cost picture before it opens. What the constraint buys today is discipline, not fear: cost stays on the record, efficiency work — like the memory diet — counts as value work rather than housekeeping, and the open question is armed where it can be answered cheaply: does token spend per unit of durable value fall, hold, or rise as an instance grows? No datum distinguishes these yet. The record that answers it is already being kept.

Nothing has landed there yet. When it does, it lands frozen, whichever way the result falls.
