# Fractal Value Model

> **CANONICAL CONCEPT DOCUMENT — Draft, explicitly non-binding (C-086).** This is the maturing home of the value model: what FRACTAL promises, to whom, through which surfaces — and the one constraint that could cap all of it. It is deliberately **not a business model**: business implies cash flow, and none of the branches below carries one. It is a **value promise** — the structure of what the project is worth before (and independent of) any monetization, which stays a layer-five question of the Network Foundation. It is **vision, not architecture** — nothing here binds a build; branches enter the working queue only through ordinary decisions when their named triggers fire. It stands beside `Fractal_Knowledge_Network_Foundation` in the concept tier: that document owns *how far the rules compose*; this one owns *where the value sits while they do*. Living document: stable filename, version tracked below (C-012).

## 0 · What this document is for

FRACTAL's value has so far been argued implicitly — in the capture, on the site, in the Network Foundation's economics. This document makes the structure explicit and gives it one maturing home, for the same three reasons the Network Foundation exists:

1. **To let the model mature in one place** across sessions instead of fragmenting into conversation records.
2. **To constrain present design cheaply** — each branch back-propagates requirements the near work can satisfy now, as armed triggers, not build orders.
3. **To be projectable.** Any public statement of "what FRACTAL is worth" — a pitch page, an about section, a grant paragraph — is a stamped C-035 projection of this document, never a second source.

**Standing limit on everything below:** entries here are *triggers and constraints*, never build orders. The corpus's discipline — build on observed need — applies to the value model itself.

## 1 · The shape — three branches, one horizon

The model is three live branches and one hypothetical horizon. The branches share a structural property that is itself fractal: **each is simultaneously a value promise outward and an experiment inward.** Every surface that delivers value to someone else also feeds the refinement-through-use loop (C-107) — the marketing arm is a test bench, the explanation is the engine sketch, the product proves itself by being used to build its own distribution. The horizon is different in kind: not a branch but a bearing — a shooting star, steered by, never steered toward as a commitment.

| # | Branch | Outward promise | Inward experiment |
|---|---|---|---|
| 1 | **FRACTAL itself** | Durable, auditable project memory across AI sessions | The system proves itself on itself (the mother is instance zero) |
| 2 | **The website — information hub** | The method, learnable and adoptable piecemeal | The engine sketch (C-119): explanation and machine co-develop |
| 3 | **The social media branch** | Distribution: knowledge reaching people where they are | Media content as a new governed content class; complexity growth under load |
| ∞ | **The knowledge network** | *(horizon — held entirely by the Network Foundation)* | — |

## 2 · Branch one — FRACTAL itself

The kernel, the governance stack, the store, the registry: the product. Its promise is the masthead sentence — *AI agents forget. Your project won't.* — made provable: session-durable context, decision provenance, machine-guarded consistency, external anchoring. This branch is the deepest and the furthest along: five anchored betas, an executable genesis, one foreign instance born from the kernel and migrated across a release seam (arc 2, KNet). Everything else rides on it; no other branch is credible if this one is not real.

**What it constrains today:** nothing new — the whole existing corpus *is* this branch's discipline.

**Far shape (v0.2):** the branch's horizon is the **enterprise offering** — organizations run as descent trees on customer-owned serving infrastructure, held in the Network Foundation §§10–11. The day a real customer exists, this document's "no cash flow" opening earns its revision: that is the branch where a business model would be born.

## 3 · Branch two — the website as information hub

The site is not marketing surface for branch one; since C-119 it is the **engine sketch** — the machine's real parts exposed verbatim and downloadable. Its standalone promise: a visitor can learn the method, take the standards, and adopt pieces **without ever birthing an instance**. That is the RF1 finding made into a branch: all three simulated adopters said *not yet — but the substrate is right*; people take the substrate before they take the system, and the registry is the adoption gate. The hub's value grows by the site content pass (the standing lane) — guide depth, paper pages, field studies — and refreshes mechanically at each tagging close (the C-119 refresh duty).

**What it constrains today:** already satisfied — the C-119 rules (parts verbatim, honest absences, prose links to anchors) *are* this branch's quality gate.

## 4 · Branch three — the social media branch

The new branch, declared this session, unbuilt. Three roles in one structure — marketing, website extension, information distributor — and its inward face is the most interesting: a **live internal experiment in how FRACTAL operates on media content**. Producing governed public content means solving, in real use, problems no current lane touches: extracting knowledge from media into md; the post as a projection class (is a thread a stamped C-035 projection of a canonical source?); provenance for content that leaves the repo and circulates; and the complexity growth of the instance that governs all of it. There is a practical limit to FRACTAL's complexity somewhere — none is in sight yet, and this branch is the probe that goes looking for it.

**Named dependencies (already on the books):**
- **The flip (C-107)** — real distribution presupposes, or interacts with, the public repo; the flip stays necessity-triggered, and this branch could become a second face of that necessity beside the registry consumer.
- **OQ-34 (the umbrella)** — a public media identity sharpens the protectable-name question; founding necessity may fire here first.

**Trigger:** a decision to open the branch — it does not open by being described here. First act when it fires: the branch's own working lane (a Local Context aspect or a Site/ extension), a declared content class, and its fieldnote lane — the experiment instrumented from the first post (C-094: field testing is the standard proving process).

**What it constrains today:** nothing to build — but the *observation* stands that every media-content design choice elsewhere (the blog-as-wiki, the standards feed) is early evidence for this branch and should be captured as such when it surfaces.

## 5 · The horizon — the knowledge network

The fourth value is the network: warm starts, the marginal increment, verification with skin in the game, and — at the far edge — the knowledge economy. **It lives entirely in `Fractal_Knowledge_Network_Foundation` (v0.3) and is not duplicated here** (C-012: one home per idea). Its status in *this* document is exactly Max's phrase: a **shooting star** — the bearing the three branches fly by, not a destination any of them is committed to reach. The Network Foundation's own discipline (triggers, not build orders; dragons named by the first child) already holds it to that.

## 6 · The constraint — token economics (the exclamation mark)

One constraint cuts across every branch and deserves first-class standing: **the work is token-heavy, and tokens are not cheap.** The record already carries hard data: the UF1 flight alone spent ~948k tokens for nine agents; the capture program ran 67 agents across four flights; the Ultracode Flight Protocol carries a *cost honesty* requirement precisely because this was already felt. The structural form of the risk is sharper than "expensive":

> **Value scales with token spend — so the failure mode is not that FRACTAL doesn't work, but that it succeeds into unaffordability. FRACTAL could become so good it needs too much gas.**

Branch-by-branch exposure: branch one's ritual overhead (the close, the checkers, the flights) is the baseline burn; branch two is nearly free (static content, refreshed mechanically); branch three would be the hungriest of all — media production and extraction are continuous token work, not per-close bursts. The horizon inherits the question at network scale, where it meets the Network Foundation's open verification-cost quantity (its §5, KNet R-12): both are the same unknown — **the cost denominator of the scaling law**.

**What it constrains today, cheaply:**
1. **Cost stays on the record.** Flights already report spend (the flight standard's cost-honesty line); that practice is this constraint's instrument and must not erode.
2. **The efficiency ratchet is value-model work.** The diet program (C-110–C-112), the compaction doctrine (C-095), the adaptive close — these are not housekeeping; they are the value model defending its own denominator. The strongest lever on the curve is named in the Network Foundation §11: **deterministic selection outside the context window** — classical code navigates, the model reads only its working set, and token spend converts into CPU time.
3. **Branch-three sizing waits for data.** No media-branch commitment before a cost picture exists for its content loop — the branch's trigger question includes *what does one governed post cost?*

**Open quantity (armed, unresolved):** the cost *curve* — does token spend per unit of durable value fall (compaction, warm contexts, better models), hold, or rise with instance complexity? No datum yet distinguishes these. The first instrumented answer likely comes from the existing record (flight reports + close sizes over the session series) at near-zero collection cost.

## 7 · What this constrains today — the summary

Almost everything this model asks for already exists, which is the point of capturing it now: branch one is the corpus, branch two is C-119, the horizon is the Network Foundation. The genuinely new obligations are three, all cheap: keep cost on the record (§6.1), treat efficiency work as value work (§6.2), and capture media-content evidence when it surfaces in existing lanes (§4). The one genuinely new *build* — the social media branch — stays behind its trigger, as it must.
