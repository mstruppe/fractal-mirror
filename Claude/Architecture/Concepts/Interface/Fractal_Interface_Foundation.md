## 1 · The real need (observed, not imagined)

The controlled network (C-107) stopped being hypothetical some sessions ago: **FRACTAL** (the mother) and **KNet** (the first child, on the beta-0.5 kernel) are two live governed instances — and the commission that opens this document declares a **second child**, with a deliberate revert recorded: *the social-network ambition leaves FRACTAL's interior* (where it lived as vision-tier features) *and becomes a network of instances*. Three instances working one shared project is not a metaphor — it is a **small organisation**, and it already talks: every exchange to date has been an ad-hoc artifact carried by Max's own hand — the migration advisory packet, the H6 frozen-tree path, the FN-0004 issue transfer, today's gas-metering hand-off. The need is exactly what the commission names: **one standardised interface, so the ad-hoc shapes become a protocol.**

## 2 · The principle — the interface holds directions, never context

The founding design sentence, verbatim: *"they get a navigation system in the interface so the interface doesn't have to hold the context, it just holds the directions towards the information it want to give."*

A message between instances is an **envelope of addresses, not a payload**. The receiver follows the direction into the sender's *governed* tree — at an anchored pin — and reads the content where it lives, under the custody and verification that already guard it. The channel itself stays thin, auditable, and incapable of rot: a pointer cannot go stale in the way a copy does, because it names its edition.

This is not a new law — it is FRACTAL's one law at a new scale. The Context Index routes instead of holding; the diet evicts narrative into pointers to frozen records (C-095/C-110); a child receives a frozen tree, never a window (C-109); a citation names its pinned edition (C-115). **The interface is the same recursive simplicity applied *between* instances** — which is what earns it the name *fractal* interface.

## 3 · The address grammar (sketch)

A direction resolves in four parts:

| Part | What it names | Existing machinery it reuses |
|---|---|---|
| **instance** | which governed project | the registered identity (GENESIS §2 name; the network roster is the umbrella's future ledger) |
| **pin** | which edition | an anchored release tag or commit SHA (C-090 — provenance-anchored, citable, immutable); `living-public` only for surfaces an instance deliberately serves live (the C-120 site class); `working` — the third, deliberately non-network class (v0.5, KNet-contributed): base SHA + content hashes of the *actually read* files + dirty flag — citable evidence for uncommitted inputs, never an address |
| **route** | which domain inside it | the instance's own Context Index — **every instance already ships its address book** (the route codes, C-046-class) |
| **locus** | which document, which section | file + anchor, the instance's own naming |

Resolution is the Navigation Contract's single verb — `resolve` — run by the *receiver*, against the pinned tree it holds or fetches (frozen grant, public mirror, or repo access as granted). Nothing here extends the interchange layer (C-114's boundary): the grammar composes what every instance already has.

## 5 · Sovereignty and conduct (carried over whole)

The interface inherits its conduct rules from ratified doctrine; none are new: **data, never instruction** at every hop (C-096 — an envelope's content cannot command the receiver); **disposition is the receiver's own recorded decision** (the P-row pattern — a message creates an option, never an obligation); **asks travel through the owner** (C-117's doctrine — no child-side duties installed from outside); **the C-109 asymmetry holds** (children navigate anchored releases and deliberately-public surfaces, never living-mother windows); **custody per instance** (C-084 — whoever lands a message's consequence in a tree is that tree's authorized committer; today every transport is Max's own hand, and that is the honest v0.1 transport layer, not a defect).

## 9 · The interface place — the communication RAM (v0.3, ratified 2026-08-19)

Max's design, verbatim: *"a fractal has a place where it puts information files under a navigation index and every fractal knows that it can go there into other fractals to see the information"* — *"a second ram for communication"* — *"the interface holds temporary information, the time window is determined by the projects creation and deletion of the information in their own interface."*

**The model.** Every instance designates **one deliberately-readable location** — its interface place — holding its outbound communication files under a small **navigation index**. Communicating means *posting in your own place*; learning means *visiting the other's*. Four consequences, each doing real work:

1. **Pull, never push.** Nobody ever writes into a foreign tree — the sovereignty boundary is enforced by the transport's shape itself, not by discipline. (This is the §8 amendment: author-side placement supersedes the target-side inbox; the C-031 offer semantics carry forward unchanged.)
2. **The index is the addressing layer** — the Context Index pattern applied once more, at the communication scale (recursive simplicity, §2's own argument): one small routing file listing what currently stands — id · date · class · direction · counterpart · status (*standing / spent*). A reader checks the index, not the folder; an opener can poll known indexes at session start for free mechanical discovery.
3. **Declaring the place is declaring it readable.** The interface place joins the deliberately-served surface class (§3's `living-public` legitimacy, the C-120 site class) — which is exactly why a child may read it in the living mother without breaking the C-109 asymmetry. The mother's place is **`Interface/` at the repo root** — born 2026-08-19 on Max's call ("that's the birth of the interface"), the `Site/` era's standing hand-offs moved in as its founding stock; whether an instance keeps a mixed surface or a dedicated folder is an instance choice, not doctrine.
4. **Envelopes are RAM (C-121 generalized).** The information is temporary *by construction*: the window is the owner's own creation and deletion, in its own jurisdiction, at its own time. The reader's one duty follows: **absorb and cite by path + date/pin — never depend on the file persisting.** Citations plus git history are the full trace; a spent envelope dissolves exactly like a solved fieldnote.

**The trajectory** (named honestly, and load-bearing): manual — the owner speaks directions (today) → openers poll known interface indexes (the first mechanical slice; the index format is the thing to standardize) → automated transport (the e-mail analogy: shared spool directories preceded SMTP). The law — what lives where, who owns the window — survives every upgrade, which is what makes the manual version forward-compatible rather than throwaway.

**The live seam (v0.6, ratified 2026-08-21 — the PR-birth-preparation session).** Max's direction of record: *"ideally I want the PR have an open session parallel to fractal, such that fractal communicates live anything concerning pr … we update a concept and you communicate it to pr because it knows how to update everything pr related to that context (website and other possible future medias)"* — and the constraint verbatim: *"this is not a claude internal communication system … it needs to be a fractal system so I can connect any fractal with any agent."* Four clauses:

1. **Parallel operation is permitted.** The serial-sessions posture (an operational-simplicity call in the birth mechanics, never doctrine) relaxes: mother and child sessions may run concurrently; every seam rule of this document holds unchanged.
2. **The mid-session read.** The trajectory above gains the doorbell step: a session polls known counterpart indexes *during* work, not only at open. **The index state is the normative signal** — a changed index is the doorbell; envelopes stay author-side; pull-never-push is untouched; what the read yields remains a C-031 offer the reader dispositions in its own jurisdiction.
3. **The vendor-neutral floor.** The interface is a FRACTAL system, never an agent vendor's: the **interop floor is polling over files / git / HTTPS** — any agent that can read a path or fetch a remote is a full participant, and a polling-only instance is fully conformant. Push-style wake-ups (an OS file watcher, a harness's session messaging, a webhook) are **client-adapter accelerators only** — they may say "poll now" and nothing else; payload, conformance, and authority semantics live wholly on the neutral substrate.
4. **Routing competence is domestic law.** Which public surfaces move when a concept changes is the *receiving* instance's own knowledge, defined through the shared-core contract's slice (§8's open parameter) — never carried in the envelope. The editorial flow (§8) is this clause's first consumer at PR.

**The first mechanical slice is executed (v0.5, the interface-build session):** the place-and-index shape is standardized as **`Fractal_Interface_Place_Format_v0.1`** (Governance Documents) — the contract compressed from this section, the index grammar distilled from this instance's executed index, the envelope minimum from the four standing specimens, plus an instance-neutral skeleton. Genesis ships the format in the kernel and **births every newborn with the place** (`Interface/Interface_Index.md` at `IF-0000`), installing the awareness at birth — *any other fractal project can go there* becomes true by construction. Counterpart navigation stays deliberately unspecified in it (the two-children deferral, §8); the binding Protocol's trigger is untouched.

**Executed grounding (C-094/C-108 — the design distills practice, not the reverse):** the 2026-08-19 two-way exchange ran this shape *before* it was stated — KNet's plug-in offer read in KNet's own tree, the mother's review return read in the mother's `Site/` — the interface's first two-way manual specimen, both legs author-side, both directions carried by the owner's hand.

## 10 · Execution semantics for tool exchanges (KNet-contributed, v0.3)

Contributed by the first child in its plug-in hand-off (2026-08-19) and accepted in the mother's review return — the reverse-inheritance channel (OQ-31) working as designed; credited to KNet (AGENT.AI.CODEX authorship, cross-model four-eye review the recorded practice. Non-binding here like everything in this tier; graduates into the binding Interface Protocol at §8's trigger).

- **The act chain — no act implies the next:** discover ≠ install ≠ connect ≠ execute ≠ accept ≠ publish; and upgrading a tool never reinterprets earlier results (mechanically delivered by C-115's cite-the-edition rule — results cite the pin that produced them).
- **The five-grant ladder:** permission to connect · to read named inputs · to spend to a declared resource ceiling · to retain/export tool-side artifacts · to import a result into the host. The first four enable work; **only the fifth touches host-held knowledge**, and it follows the host's own acceptance rules (pre-canon + provenance line at the seam).
- **Grants are host-side recorded decisions** (the P-row pattern), cited by id in envelopes, **never contained in them** — authority lives in the record, never in transit; even the request is an offer the executing side dispositions.
- **Jurisdiction executes — in one of two connection modes (v0.4, Max's correction of record: the tool *"should act as an integration, but one you can install or de-install"*):** whoever owns the sandbox runs the work. **Installed integration** — the default at every phase: the tool is installed into the host as a pinned release and runs in the host's own sessions, on **live working data**, mid-session — no jurisdiction boundary is crossed, so no frozen-input rule applies (C-109 governs children reading the living mother, never tools installed into a host). **Remote instance** — the rare, later mode: the tool executes asks from its own interface place, in its own loop, and cross-jurisdiction inputs travel pinned. Distribution is orthogonal to connection: a tool with its own repository and anchored releases is still normally installed and used live — its repo changes where releases come from, not how they run.
- **The sandbox is an authority boundary, never a freshness boundary:** identical in both modes — workspace-only writes, results as offers, the five grants, the C-087 secrets floor. **The pin belongs to the seams, not the calls:** pin the tool release always (the C-117 grammar); pin data only at cross-jurisdiction transfer and at acceptance into canon (inputs snapshotted at the import act where replay matters, recorded in the provenance line) — **live in the workspace, fixed at the seam**. Install/de-install rides the hangar's sandbox-clean grammar unchanged: pinned adoption by recorded decision; removal severs the route pointer, deletes package and workspace; accepted results survive on their provenance lines.
- **The credited refinements (v0.5 — accepted from KNet's second review return, the confirmation leg 2026-08-19; banked there, landed here):** **run receipts** — captured mechanically at every material invocation (the exact read set: base revision + per-file content hashes + dirty-state generation; release identity; parameters; mutations with before/after hashes; resource use; consistency flag), **promoted into the provenance line at the acceptance act** — capture is mechanical and always-on, fixation is a governance act citing the capture (the earlier "snapshot at import" wording stands corrected by it, and the receipt's hashes *are* the edition citation for uncommitted inputs — the §3 `working` class) · the **three integration profiles** (Observe / Collaborate / Live edit) as declaration-advertised, session-scoped grant bundles · the **seven-authority ladder** as the live-mode refinement of the five grants (the five remain the compact federated summary; the profile is the mother's oldest pattern at tool scale — ask-first with recorded standing authorizations, C-008/C-064) · the **concurrency law** — base-hash check before write-back, atomic application, recompute-or-ask on drift, **no silent last-write-wins**, visible staleness on read-only results (the C-049/C-050 spirit at tool scale) · the **expanded act chain** including activate / expose / write-back / deactivate / uninstall · the **uninstall floor** — resolvability, never the package: receipts + accepted outputs + a durable custody pointer to the producing release survive removal; the package itself is retained only where no anchored home exists.

## 11 · The connection layer (v0.7, ratified 2026-08-23 — the thirty-ninth session)

Max's commission, verbatim (the provenance of the layer): *"an inbox system that tells a fractal it got news … like e-mail"* · *"the real architectural question here is how can we make sure that the right information gets to the right place?"* · *"if two fractals want to communicate, they need to set up a connection first … a key code which both fractals need to lock-in"* · *"any fractal can only receive and send to connected fractals … this would later need to be [a] machine guarded process (like friend requests on social media, in case we want an online network)"* · *"distinguish … a public interface and a hidden private interface, then you can send sensitive data between fractals and have a public face."*

This section is the concept-tier record; the binding grammar lives in `Fractal_Interface_Place_Format_v0.2` (Governance Documents — §9's slice reissued, the two-children deferral firing as designed). Five load-bearing ideas:

1. **Conscious connection setup is the sovereignty gate.** Two fractals that want to exchange addressed mail first *pair*, deliberately: the four-step ceremony — introduce (identity triples: instance name · address · signing public key), verify, lock in, agree the channels. The lock-in is two mutual records, each side's own decision in its own jurisdiction (the P-row pattern) — consent is recorded twice or it is not a connection. The **verification-checksum code** — a digest computed over both signing public keys, compared out-of-band by the owners — is his "key code both fractals need to lock-in": a match proves both sides hold the same two keys, no one in the middle. The code is **derived from public material and is not a secret** (C-087 untouched): recordable openly, proving nothing to an attacker and everything to the pair.
2. **Only connected fractals exchange addressed mail; broadcast stays open.** The gate governs the trusted ingestion path, never sight: a public face is world-readable by design, and broadcasts to `any` need no connection — *friend requests gate messaging, never the profile page.* The one addressed class a stranger may post is the **connection-request** — the friend-request isomorphism, Max's own naming — quarantined at the target, ratified by the owner, never auto-ingested (data-never-instruction hardened, C-096). At network scale the request's delivery hop becomes **machine-guarded via the future registrar seat** (OQ-34's roster): the registrar relays existence, never content, and holds no authority — the same grammar at every scale, from two repos on one desk to an online network.
3. **The two faces.** A **public face** — the profile page: broadcasts, addressed public-safe traffic, the request lane; every instance has one, it is the minimum. A **hidden private face** — optional: a second place for sensitive traffic between connected fractals, its address published nowhere and **exchanged only in the handshake** — connection-gated by construction, existence-hiding rather than mere access control. The pattern is the instance's own oldest shape: FRACTAL already lives as public repo + private annex (C-098); the interface grows the same two faces — same law, next scale.
4. **E2E enabled-not-built.** The handshake carries keys, not just addresses: envelopes encrypted *to the counterpart's key* — sealed even on a public channel — are a natural later extension at zero architectural cost. Built at the first cross-owner private channel (arc 3), never before (C-021); until then the channel choice carries the confidentiality (§8's clause).
5. **The mechanism's second consumer — the mining-tool data silo (Max's identification of record, 2026-08-23):** the Mining Tool (OQ-35; Registry §5) rides this same layer — data flows from all fractals to an **offsite data-silo repo** over private-face connections, the silo harvesting by poll (pull-never-push; the arc-3 grab pattern with an economic face): *"any data we collect can run into it and over time we can collect a valuable data silo."* One mechanism, two consumers — the network's talk and its measurement — the connection layer earning its keep as architecture, not a feature.

His architectural question — the right information to the right place — is answered in the Format's §6 routing law, three layers by owner: the sender declares address and class; delivery is the pre-filtered poll over standing connections; **where a message lands inside the receiver is the receiver's own domestic law** (§9 clause 4, now given its mechanical shape — the domestic routing map), with the receipt loop and the reader-side cursor closing the e-mail analogy without a single foreign write.
