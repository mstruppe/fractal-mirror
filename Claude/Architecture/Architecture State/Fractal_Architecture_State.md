## 2. The knowledge core — KG

*The load-bearing architecture, realised and live.* Canonical documents: **Knowledge Path Foundation v0.1**, **Node & Event Schema v0.6**, **Node Template v0.5**, **Navigation Contract v0.1** (`/Claude/Architecture/Concepts/Knowledge Graph/`), and the live **Knowledge Graph Store** (`/Claude/Knowledge Graph Store/`).

- **Two relations, one log (C-014).** Everything is an Entity with a stable identity (`TYPE-ULID`, C-015/C-039); every classification, containment, citation, authorship or membership is a Placement edge in one append-only event log (C-022–C-025) — physically **one active file**, rolled only by the recorded ceremony (C-055). The log is canonical; node files are a materialized fold (C-024).
- **Context is separate from identity (C-016).** Independent facet namespaces, dotted coordinate codes, prefix tracing; facets themselves are minted concepts (C-043); routing codes derive from identity via `alias(kind: route)` bindings (C-045/C-046). **Document identity mirrors file identity (C-061):** living documents hold one revised DOC node; versioned artifacts (specs, protocols) hold one DOC per version file, the versionless alias riding the series pointer — every version of a governing spec is a citable identity.
- **Multi-writer safe (C-049/C-050).** First-mint-wins collision policy, append-only cure, root ceremony; `verify.py`/`mint.py`/`check_versions.py`/`close.py`/`genesis.py` repo-resident (C-050/C-060/C-073 — the fourth tool automates the close's mechanical ripple, the fifth births a new instance; both drone-built); the fold ritual is a standing duty at every store-touching commit, the version-agreement ritual at every close — the store's internal consistency and the corpus's prose claims are both machine-checked.
- **The read side is contracted (C-068–C-070).** Navigation has its own canonical specification — the **Navigation Contract** (companion to the Schema: what is written vs how it is read, refreshing independently): entry is a query shape over existing structure (no home node — axes, prefix descent, weight-ranked landmarks); trace is bounded ranked recursion over four hops with a deterministic weight-product order; facets are independent, entities the junctions; derivation is a role-filtered trace; redirects accept stale and emit canonical. Read verbs: `resolve`/`enter`/`trace`/`history`. Implementation tiers: the grep ritual (live) → the index server (= the `verify.py` fold persisted; deferred per C-021, trigger sharpened: inverted-view reads becoming routine) → the Galaxy UI (§4).

## 3. Ontology — ONT (what exists)

*Settled by C-017 (Ratified); recorded here against the older model (decision C-052).*

A node's **shell is behaviour, not class**: the same Entity, one identity, can wear either face —

- **Galaxy — the container face.** Open it and see what is placed inside (containment edges pointing in). The "GS" of the ChatGPT-era UI vision.
- **Operator — the application face.** Invoke it; inputs flow in, outputs flow out, and **a run appends provenance edges** — the log records not just where things sit but how they were made. The "OS" of the ChatGPT-era vision; the capability/plug-in thinking of Master Index Parts VIII (capability contracts, typed ports, adapters) remains the richest exploration of this face and is inherited as *direction*, pointer-only.

**Supersession record (C-052):** the ChatGPT-era *current two-shell model* — Galaxy Shell and Operator Shell as two fundamental object **classes** (its ledger item 69.5) — is superseded by C-017's two-**faces**-of-one-node. The Master Index's open questions 13.8 ("can a shell change class?") and 13.9 ("can one object embody both roles?") are thereby answered: yes, trivially — faces are worn, not assigned; both faces share one Entity and one set of Relationships. This is what makes the reversible split-screen navigation of the UI vision possible at all.

## 6. Instantiation — kernel and instance (the shipping layer)

*Declared 2026-08-15 (C-078); **partition measured the same day** (arc 1, per v0.30) — the counts and classes below are the executed result, superseding this section's first-issue estimate.*

FRACTAL has so far governed exactly one project: itself. Everything mapped above describes a **grown instance**, in which the portable substrate and this project's own biography are interleaved in a single repository. Governing *other* projects requires naming that seam. Naming it changes nothing on disk.

**The partition is three-way, not two.** The first issue of this section assumed kernel vs instance. Walking all 79 decisions produced a third class that cannot be collapsed into either — and it is the operationally important one, because it is exactly the input a genesis tool must ask for:

- **Kernel (~64) — inherited as given.** The whole KG format and read side (C-014–C-020, C-022–C-027, C-039–C-046, C-049–C-050, C-055, C-061, C-068–C-070); conduct and method (C-001, C-003, C-004, C-006, C-008–C-012, C-028, C-030–C-036); ritual and guard (C-057–C-060, C-065–C-067, C-071, C-073–C-077, C-079). These an instance inherits **as constitution** and does not re-decide.
- **Parameterized (7) — kernel rule, instance value.** `C-005` the identity scheme (rule) vs the `Fractal_` prefix (value) · `C-037` the commit convention vs the writer identities · `C-038` ship a bootstrap vs its content · `C-046` routes are alias bindings vs *which* routes · `C-056` keep an off-site copy vs which host · `C-059` walk a refresh checklist vs which rows · `C-062` label pre-canon material vs which file.
- **Instance (14) — biography; does not travel.** C-007, C-013, C-021, C-029, C-032, C-051–C-054, C-063, C-064, C-072, C-078 — plus C-002, retired by C-067 and therefore travelling as neither. With them: the Protocol series, Local Contexts, Return Packages, Scans, Global Context §1–§2, the store's own nodes and events, and the roots `KG` and `AST`, which name FRACTAL's own architecture rather than any project's.

**Measured consequence: FRACTAL is ~80% kernel** — materially more portable than this section's first estimate (~40) claimed. An instance starts its own numbering above the inherited line rather than from C-001, and the parameterized set is the entire input form of genesis.

**The kernel is tiered (C-079).** Kernel membership is not one flat list: FRACTAL ships **specifications** as kernel and lets implementations be optional. The **Navigation Contract is kernel**; its implementations are tiers — **tier 0**, the grep ritual, requires nothing beyond the repo and is where every new instance starts (§2 already named it conformant; C-079 makes that membership normative); **tier 1**, the `resolve`/`enter`/`trace`/`history` index server, is **kernel-optional**, built by an instance whose scale demands it on the C-068 trigger. An index is a C-019 derived, disposable cache and therefore cannot be load-bearing for a seam that runs through canonical text; a newborn instance has near-zero nodes, where grep is not merely adequate but correct. This tiering is also the mechanism the weight-dial question (OQ-28) will use — *minimum viable* is answered by tier membership rather than by cutting features. Recorded consequence: the **skill** packaging tier completes in the extraction arc, the **plugin** tier does not, since `BOOTSTRAP.md` §2.2 defines the plugin as *skill + MCP index server + entry commands*.

**Tiering generalizes (C-079's second member).** The index server is not a special case. The **Agenda Board** (C-047/C-048) is likewise a display projection, not load-bearing — kernel-optional, tier 1. C-079 therefore named a *pattern*: every kernel component is either **tier 0** (required for an instance to have memory across sessions at all) or **tier 1** (earned on observed need). The tier-0 set is provisionally the spine (Global/Local/Index), the store format with `mint.py` + `verify.py`, the commit convention, the Register, the close ritual, and one adapter; everything else — Board, `check_versions.py`, the protocol series, Scans, the drone tier, signing, the index server — is tier 1. **Provisional by design:** OQ-28 resolves this from arc 2's lived experience, not from arc 1's design.

**Genesis — landed and exercised (`GENESIS.md`, stamp inside per C-012, + `genesis.py`).** `BOOTSTRAP.md` answers *rebuild this instance from its own history* — backward-looking, drill-proven (C-038). `GENESIS.md` answers the forward question: *birth a new instance with an inherited constitution and an empty history.* The two are siblings at the root and refer to each other; neither subsumes the other. **Arc 1 is complete:** the executing tool is the fifth store tool (`genesis.py` — drone-built, gated by the governing surface in an independently birthed instance), and the packaging unit is resolved (C-083 — the adapter plus `.claude/commands/`; the queued `SKILL.md` **retired unbuilt**, since a second projection of the conduct source on one surface is the drift class C-067 closed). The skill tier had landed slice by slice without being named done; the plugin tier stays open behind a tier-1 index (C-079).

**The acceptance test is no longer a prediction.** GENESIS §0 claims a stranger can birth an instance and close a session in it. That was executed twice — the second run a **control** on a freshly birthed instance, confirming the first run's three findings cured in the *generator* rather than in one repo. What it proves architecturally is narrow and load-bearing: **the loop survives instantiation.** A session opened on a spine with no history, recorded a decision that *binds* an inherited rule rather than re-deriving it (`P-001`, citing C-079 without copying a row, `P-` and `C-` never colliding), issued a handover a successor can read, and closed with the store verifying.

**The first real instantiation exists (2026-08-15, per v0.37).** Not scratch: **KNet** (`github.com/mstruppe/knet`) — a research instance on the information economics of knowledge networks — was birthed from the anchored `beta-0.1` tag by Max acting as the kernel's first stranger, and passed the §6 acceptance the same day: its own roots and routes, its own AI writer attributed from the first commit, `P-001` above the inherited line, a hand-walked tier-0 close, and — within hours — a governance edge case (a close invalid at issue) detected and repaired under its own constitution, producing doctrine the upstream corpus does not yet hold. The kernel now governs two projects, each in its own jurisdiction; the instantiation seam this section names is no longer forward-looking anywhere but §6's federation paragraph.

**The kernel is not biography-free (C-081, measured) — and the disposition is now decided (C-088).** Copied kernel documents cite the history of the instance they came from: **67 dangling citations** in a newborn — the Rule Overview naming Protocols v0.1–v0.30, the Schema its superseded versions, the Settings the protocols that ratified them. Each is a true statement upstream and a phantom downstream, and *frozen* status does not exempt it (`check_versions.py` rule B pierces frozen by design). **C-088 (2026-08-15) rules the biography *provenance, not defect*:** the cure is an **`INHERITED` source class** — a downstream instance's `check_versions.py` exempts citations from inherited kernel documents into the upstream history they came from, while intra-instance claims still check; stripping revision histories on copy was **rejected** (silence bought at the cost of the constitution's *why* and byte-identical provenance). The machinery **landed the same session** (drone flight 4, gated per C-081/C-082): the `INHERITED` class, `genesis.py`'s registry projection (the 9), and the `.inherited` manifest — the gate executed on an independent scratch birth at **76 → 0 errors**, and `doctor.py` joined as the **sixth store tool**. `verify.py` alone remains the genesis gate for a newborn — carrying the checker is not being required to run it. The 67 stays the second number on OQ-28's dial, beside the kernel's ~20,000 words of mandatory prose.

**Federation — the layered verdict (deferred; OQ-31).** Two instances already merge cleanly at the **identity** layer: ids are `TYPE-ULID` with an 80-bit random tail, so independently built stores never collide, and merging logs is concatenate-and-sort — precisely what the tools' `load_log` already does. They collide at the **code** layer *by design*: codes form one global namespace across all facets (C-044) under first-mint-wins (C-049), so every instance anywhere mints its own `GOV`, `CTX`, `AGENT.HUMAN.*`. `verify.py` already **refuses such a merge loudly** (`CODE COLLISION`) — the substrate fails safe, and the existing cure (re-mint the loser + redirect) is built for accidental collisions between two writers in one project, not for ingesting a foreign namespace. The cure is therefore an **origin layer** — foreign codes never enter the local namespace at all — not a relaxed guard. The **meaning** layer stays human by doctrine: a foreign graph arrives whole, namespaced and attributed, and equivalence is asserted by minted bridge events, never inferred (C-018's "human retains interpretation", applied at graph scale).
