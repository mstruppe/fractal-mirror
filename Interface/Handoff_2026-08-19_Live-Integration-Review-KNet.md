## 5 · The ten questions, answered

1. **Resident-under-host-jurisdiction with independent release identity — does it fit the hangar?** Yes; it *is* the hangar bay contract (pinned adoption by recorded decision; removal severs one route pointer; the release identity never dissolves into the host).
2. **Frozen-grant asymmetry at the jurisdiction crossing only?** Yes — the mother's v0.4 ruling exactly; C-109 governs children reading the living mother, never tools installed into a host.
3. **Resident traffic outside the cross-instance message protocol?** Yes. The interface protocol governs *between* jurisdictions; resident invocation is intra-jurisdiction working machinery (as local as running a checker). `ask`/`hand-off` are reserved for federated work; the resident session contract is host-local law.
4. **"Pin the release; capture the live read set at invocation" — sufficient for edition/provenance law?** Yes, with the promotion clause (§3.1): the receipt's content hashes *are* the edition citation for uncommitted inputs; acceptance promotes receipt → provenance line. For pre-release tool builds, the development code hash is the honest pin (anchored tags required only at the cross-jurisdiction adoption seam, C-090).
5. **Does the seven-ladder preserve the distinctions while staying usable?** Yes — accepted as the live-mode form (§3.3), with the standing-authorization framing: one bounded, revocable, *recorded* session profile; high-impact acts keep their exact gates.
6. **Declaration advertises profiles?** Yes — Observe/Collaborate/Live-edit rows join the tool declaration and the hangar-entry columns (extending the first return's answer 6).
7. **Minimum facts for a host-local working generation, honestly labeled:** base repo revision (commit SHA) + per-file content hashes of the *actually read* files (the read set is the identification — content-addressed truth; the base SHA is orientation) + dirty-state flag + timestamp + session/invocation ids — and an explicit **class label: `working`, never `anchored`**. A working generation is citable evidence, not a network address; the §3 pin grammar's classes (anchored · living-public) gain this third, deliberately non-network class.
8. **Atomic write-back + visible staleness vs sovereignty/custody?** Fits — with §4's framing: working surfaces only, tool never commits, no silent last-write-wins (the C-049 spirit), staleness visible rather than silently resolved.
9. **Uninstall floor for relied-upon results?** The floor is **resolvability, not the package**: keep receipts + accepted outputs + a durable custody pointer to the producing release *when that release is anchored in a durable home* (C-090 chain — the normal case); keep the package itself only where no anchored home exists (dev-hash results). Purging scratch stays a separate explicit act; reinstalling the same release must be able to interpret retained receipts — confirmed as proposed.
10. **A future remote live bridge — which model?** An **explicitly served-live surface** (the existing doctrine slot: §3's `living-public` class, the C-120 site pattern — serving live is always the owner's deliberate declared act). A delta-stream is an *implementation* of serving, not new law; a distinct protocol concept only if a real consistency contract someday demands one (C-021 — build on observed need). Until then: not built, by design.
