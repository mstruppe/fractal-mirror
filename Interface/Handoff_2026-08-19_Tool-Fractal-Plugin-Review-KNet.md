## 3 · Corrections and constraints (mother-side law where an exchange touches it)

1. **The interface is a protocol, never a mother-run service.** The proposal's phrase "reachable through the mother project's interface" risks a hub reading. The mother authors the *standard*; reaching a tool means addressing **the tool's own instance** at a pin. Discovery and address lookup may resolve through the future government seat's **Network Manifest** (OQ-34's seat doctrine: the seat holds *law, addresses, and returns — never members' knowledge*; the mother plays seat pro tem); a dispatcher relays envelopes, it never rewrites, executes, or holds working context. No central relay is ever load-bearing.
2. **Authority never travels in an envelope — not even by citation of convenience.** The five grants are **host-side recorded decisions** (the P-row pattern). An envelope may *cite* a grant's id; it must never *contain* the authority. Even the request itself is an offer the executing side dispositions (the ask class's law). This keeps data-never-instruction pure in both directions.
3. **Secrets never cross the boundary (C-087).** The tool declaration lists "requested data routes and permissions" — add the hard floor: **no credential value ever enters an envelope, a workspace, or any governed artifact**, either direction. If a tool operation needs an external service, the credential stays in the *executing* side's environment layer; the envelope names the *fact* of the need, never the value.
4. **Two connection modes; the sandbox is an authority boundary, never a freshness boundary (corrected in-review on Max's objection — the ratified rule).** **Installed integration** — the default, and the normal mode at every phase: the tool is installed into the host as a pinned release and runs *inside the host's own jurisdiction and sessions*, on **live working data**, per call, mid-session — no jurisdiction boundary is crossed, and C-109 was never about this case (it governs children reading the living mother, not tools installed into a host). **Remote instance** — the rare, later mode: the tool executes elsewhere as its own instance, and *there* inputs travel as addressed, **pinned** references (the frozen-grant asymmetry applies; the H6 grant the executed precedent). In both modes the boundary law is identical, and it is about **authority**: workspace-only writes, results as offers, the five grants, no secrets in the workspace (C-087). **The pin belongs to the seams, not the calls:** pin the *tool release* always (upgrade by recorded decision, C-117); pin *data* only at cross-jurisdiction transfer and at **acceptance into canon** — a live-computed result that gets imported snapshots its inputs at the moment of acceptance where replay matters, recorded in the provenance line. In one sentence: **live in the workspace, fixed at the seam.** And distribution is orthogonal to connection: a tool with its own repository and anchored releases is still normally *installed* and used live — its repo changes where releases come from, not how they run.
5. **Cross-jurisdiction adoption requires an anchored pin (C-090).** While the tool lives beside KNet (phase 1), it runs in KNet's jurisdiction and may be pre-anchor. The moment any *other* instance adopts it, the adopted release must be a **signed, externally timestamped tag** — pinned adoption needs anchored pins. Anchor-at-the-seam, not before (this is the sibling form of "children navigate anchored releases").
6. **Upgrade and lineage ride existing machinery — do not invent parallel machinery.** Tool upgrades follow the **Kernel Migration Procedure's grammar** (C-117): pin-never-follow, per-change recorded decision, and **results keep citing the pin that produced them** (C-115 — a citation names its edition), which mechanically delivers "upgrade ≠ reinterpret earlier results." Imported results enter the host **pre-canon (C-062) with a mandatory provenance line** (source instance · release pin · operation · date — the A1 landing-zone rule generalized); if later republished or bridged, the chain carries whole (C-088's inherited-provenance pattern).
7. **One vocabulary.** Mother naming, already public on the site: **tool-fractal** (the instance class), **the hangar** (the catalog of heavy extensions; a **bay** is one entry), **fractal sandbox extensions** (the public term of art), **connector/adapter** (host-side glue). Recommend KNet adopt these words so the network grows one language; "plug-in" is fine informally.

## 4 · The nine questions, answered

1. **Addressing: both, by phase — and the existing grammar already covers it.** The address is always the four-part direction (**instance · pin · route · locus**, Interface Foundation §3). Phase 1: the tool is a *route inside KNet* (instance = KNet). Phase 2+: the tool is **its own instance** with its own pins. The hangar entry is a *catalog row pointing at an address + pin* — it describes, it never addresses.
2. **Message classes: ask + hand-off suffice; no new class.** The request is an **ask** (dispositioned by the executing side's own decision); the result is a **hand-off** (a datum offered, accepted only by the host's explicit act). The mother's canon holds the ask as the implied sixth class that "enters when it first executes" — **the first real tool invocation will be exactly that first execution**, so the connector work doubles as the ask class's proving run. The capability declaration is not a message at all: it is the hangar entry's content, shipped inside the release.
3. **Minimal envelope:** `from` (instance + author) · `to` (instance) · `class` (ask) · `operation` (capability + parameters) · `inputs` (a list of four-part *directions*, pinned) · `limits` (resource ceiling; desired assurance tier) · `grants` (host-side decision ids cited, never contained) · `return` (the sender's inbox path — itself a direction) · `pin` of the tool release addressed. **Format recommendation:** carry the machine half as a **fenced machine-readable block with prose judgment beneath** — the fact/judgment division (C-073) both kernels already parse in the Fieldnote Format; reuse of the shared block grammar beats a new syntax.
4. **Division:** the **mother interface** owns the address grammar, message classes, envelope fact-layer format, pin semantics, the provenance-line rule, and the conduct law (data-never-instruction, offers-never-obligations). A **shared adapter** owns envelope construction/parsing only — and for phase 1 that adapter is legitimately *a file convention plus the opener*, no code. The **tool** owns operations, verification, evidence, workspace lifecycle, resource reporting. The **host** owns grants, disposition, import, publication. Execution follows jurisdiction: **whoever owns the sandbox executes.** In the installed mode — the default at *every* phase — the host runs the pinned package locally, live; in the remote mode, the tool instance executes asks from its own interface place in its own sessions. Moving the tool to its own repository moves distribution, never execution (§3.4).
5. **Grants and ceilings without payload weight:** grants as cited decision ids (see §3.2); ceilings as plain declared numbers in the envelope; large material never in the envelope at all — inputs are pinned directions the executor resolves, outputs are pinned directions the host resolves (their §4 already says this; the mother confirms it as law, not preference).
6. **Hangar lifecycle columns:** identity · current anchored release + prior pins · interface/adapter compatibility span · capability families · declaration pointer (the declaration itself ships *inside* the release — self-describing, single source; the row only points) · adoption status per known adopter (honest statuses, C-113) · deprecation note with named successor where one exists · removal rule (which route pointer severs; confirmation that accepted results survive on their pins). Upgrade/deprecation grammar = C-117's, unchanged.
7. **Origin and lineage on import:** pre-canon entry + mandatory provenance line at the seam (source instance · pin · operation · date); store-level ingestion names the origin as its own layer (the arc-3 federation verdict: foreign material arrives whole and attributed; equivalence is asserted by explicit bridge events, never inferred); republication carries the chain (C-088). A host that imports, then publishes, publishes *its acceptance of* the result — the tool's authorship stays visible in the line.
8. **Forward-compatibility constraints for the analog exchange:** (a) every envelope names direction, class, pin, and return address in its header — machine-block form recommended (see answer 3); (b) files land in the *target's* repo and are read by the target's opener at session start (the C-031 queue slot) — sender never writes conclusions into the target's canon; (c) one exchange, one file, immutably named (`Handoff_<date>_<topic>.md` — the established class); (d) anchor references by pin, never by branch. Hold those four and the software transport becomes an automation of an unchanged shape — which is the definition of forward-compatible here.
9. **When does offsite infrastructure become its own governed fractal?** The trigger is **serving**: the moment a repository or runtime holds state *other instances depend on* (beyond distributing anchored releases, which the mirror pattern already covers), it earns its own jurisdiction, custody, and governance — the executed precedent is the gate repo (`knet-gate`: born outside FRACTAL's jurisdiction, assigned to the umbrella when it forms). A remote *runtime* stays a deployment mode until that same test fires. Corollary the mother adds from its own new work: the planned measurement data repo (mother-side OQ-35, the network instrument) will cross this exact threshold and will be governed accordingly — tool workspaces and instrument envelopes should expect the same rule.
